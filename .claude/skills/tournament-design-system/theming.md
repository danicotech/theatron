# 活動主題(per-event theming)

每個活動可以有自己的外觀,但**元件一行都不改**。

## 運作方式

主題是**資料**,不是程式碼。存在 `tournaments.theme` (JSONB),core 隨 `/api/state` 回傳,前端注入成第 1 層 CSS 變數。

```
資料庫 theme JSON → core 回傳 → web 注入 <style> → 覆寫第 1 層 → 語意 slot 自動跟著變
```

換一個活動的外觀 **不需要重新部署**。這是整個設計的目的。

```tsx
// 注入點:只有這一個地方
<style>{`[data-theme="${t.id}"]{${toCssVars(t.theme)}}`}</style>
```

## 主題契約

**不是什麼都能改。** 開放太多,每個活動的版面都會壞掉。

### 可自訂

| 項目 | 說明 |
|---|---|
| 第 1 層色值 | 六個中性階 + 三個語意色 |
| 顯示字體 | `--font-display` 一個(內文與數字字體不動) |
| 圓角尺度 | 三個值等比縮放,`0` = 全直角(硬派賽事) |
| 背景紋理 | `none` / `grid`(LED 網格)/ `scanline` |
| 首頁 3D 場景變體 | `bracket` / `arena` / `none` |
| 活動標誌 | 圖檔 URL |

### 不可自訂(硬性)

| 項目 | 為什麼 |
|---|---|
| 間距與字級尺度 | 一旦可調,版面必壞 |
| `--font-mono` | 賠率欄位對齊是功能,不是風格 |
| **語意色的職責** | 可以改「金色是哪個金」,不能讓金色代表勝利 |
| 元件結構與互動模式 | 那是產品,不是外觀 |

最後一條最重要。**跨活動的一致性本身就是價值** —— 玩家換一個活動不該要重新學怎麼下注。

## 主題定義

```json
{
  "id": "summer-cup-2026",
  "name": "夏季盃",
  "primitives": {
    "neutral": ["#0B1A17", "#132A24", "#1B3A31", "#2F6B58", "#8FBFAE", "#EAF5F0"],
    "money": "#F2B705", "win": "#5BD8A0", "live": "#FF6B4A"
  },
  "displayFont": "Bebas Neue",
  "radiusScale": 0,
  "texture": "scanline",
  "heroScene": "arena"
}
```

`neutral` 六個值由深到淺,依序對應到第 1 層的六個中性階。

## 建立新主題時

1. 從主題自己的世界找語彙(見 `vernacular.md`),不要從「什麼風格流行」找
2. 對照 `slop-review.md` 檢查 —— 換皮很容易換到某個 AI 預設上
3. 三個語意色必須彼此可辨,且都通過 WCAG AA
4. 在 `/kitchen-sink` 路由套上去看一遍所有元件,不要只看首頁

## 驗收

新主題套上去之後:

- [ ] 賽程樹、投注單、商店、管理頁全部沒有破版
- [ ] 沒有任何元件因為換主題而看不見(硬編碼顏色的徵兆)
- [ ] 手機與桌機都檢查過
- [ ] 對比度過 AA

**如果換主題會弄壞某個元件,那個元件寫死了顏色。** 去修元件,不要調主題來配合它。
